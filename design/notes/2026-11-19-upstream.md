# Upstream research — 2026-11-19

This is a source review, not a successful standalone integration test. The
commits below identify the evidence examined; they are **not** selected
project dependencies or compatibility guarantees.

## Dataview

- At commit `5ad0994ff384cbb797de382e7edff2388141b73a`, the
  [plugin API](https://github.com/blacksmithgu/obsidian-dataview/blob/5ad0994ff384cbb797de382e7edff2388141b73a/src/api/plugin-api.ts)
  imports Obsidian types and `FullIndex`, exposes page lookups and `pagePaths`,
  and dispatches declarative queries to list, table, task, and calendar
  execution. This is a useful candidate for reuse, but the API's dependence
  on the plugin environment and index must be resolved.
- Its [package metadata](https://github.com/blacksmithgu/obsidian-dataview/blob/5ad0994ff384cbb797de382e7edff2388141b73a/package.json)
  declares a library entry point and library build as well as an Obsidian
  plugin build. These declarations alone do not prove that the published
  package exports the needed pieces or works in a standalone Node process.
- The [license](https://github.com/blacksmithgu/obsidian-dataview/blob/5ad0994ff384cbb797de382e7edff2388141b73a/LICENSE.txt)
  is MIT; preserve its copyright and permission notice when required.

## Breadcrumbs

- At commit `4d8accf91792295025e4b479b701e67139a1fbb1`, the
  [plugin API](https://github.com/michaelpporter/breadcrumbs/blob/4d8accf91792295025e4b479b701e67139a1fbb1/src/api/index.ts)
  reads settings from the plugin, rebuilds its graph, and returns outgoing
  edges through `get_neighbours`. It is not by itself a standalone graph API.
- The [traversal facade](https://github.com/michaelpporter/breadcrumbs/blob/4d8accf91792295025e4b479b701e67139a1fbb1/src/graph/traversal.ts)
  uses a WebAssembly graph module with depth, field and visit limits, and
  accepts a Dataview-derived path allowlist. It requires explicit freeing of
  live traversal results. Investigate both graph construction and the WASM
  build/loading path before choosing an integration.
- Its [package metadata](https://github.com/michaelpporter/breadcrumbs/blob/4d8accf91792295025e4b479b701e67139a1fbb1/package.json)
  shows a plugin-oriented entry point and a Bun/Rust/WASM build workflow.
  Whether a subset can be packaged and run in Node without modification
  remains untested.
- The [license](https://github.com/michaelpporter/breadcrumbs/blob/4d8accf91792295025e4b479b701e67139a1fbb1/LICENSE.md)
  is MIT with notices for both SkepticMystic and Michael Porter; preserve the
  applicable notices.

## Questions for the integration spike

1. Can the chosen Dataview modules construct and query an index with a
   filesystem-backed Obsidian adapter, without DOM, Obsidian runtime, or
   persistent browser storage? Which declarative query features work?
2. Which Breadcrumbs settings, sources, inferred edges and Dataview
   dependencies determine its graph? Can its WASM module and graph builders
   run in Node without changes and free all allocated resources?
3. How do both plugins resolve links, frontmatter, inline fields, paths and
   ambiguous filenames at the chosen revisions? Which Obsidian services
   must be mirrored to match them?
4. What package/submodule arrangement can reproduce builds and preserve
   upstream licenses? What Node/OS and Obsidian version combinations are
   actually supportable?
5. What can be verified against a real Obsidian oracle, and which behaviors
   or configuration cases must be declared unsupported?
