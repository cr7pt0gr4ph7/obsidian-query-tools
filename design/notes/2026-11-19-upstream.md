## Breadcrumbs

- At commit `4d8accf91792295025e4b479b701e67139a1fbb1`, the
  [plugin API](https://github.com/michaelpporter/breadcrumbs/blob/4d8accf91792295025e4b479b701e67139a1fbb1/src/api/index.ts)
  reads settings from the plugin, rebuilds its graph, and returns outgoing
  edges through `get_neighbours`. It is not by itself a standalone graph API.
- The [traversal facade](https://github.com/michaelpporter/breadcrumbs/blob/4d8accf91792295025e4b479b701e67139a1fbb1/src/graph/traversal.ts)
  uses a WebAssembly graph module with depth, field and visit limits, and
  accepts a Dataview-derived path allowlist. It requires explicit freeing of
  live traversal results. Investigate both graph construction and the WASM
  build/loading path before choosing an integration.
- Its [package metadata](https://github.com/michaelpporter/breadcrumbs/blob/4d8accf91792295025e4b479b701e67139a1fbb1/package.json)
  shows a plugin-oriented entry point and a Bun/Rust/WASM build workflow.
  Whether a subset can be packaged and run in Node without modification
  remains untested.
- The [license](https://github.com/michaelpporter/breadcrumbs/blob/4d8accf91792295025e4b479b701e67139a1fbb1/LICENSE.md)
  is MIT with notices for both SkepticMystic and Michael Porter; preserve the
  applicable notices.

## Questions for the integration spike

1. Can the chosen Dataview modules construct and query an index with a
   filesystem-backed Obsidian adapter, without DOM, Obsidian runtime, or
   persistent browser storage? Which declarative query features work?
2. Which Breadcrumbs settings, sources, inferred edges and Dataview
   dependencies determine its graph? Can its WASM module and graph builders
   run in Node without changes and free all allocated resources?
3. How do both plugins resolve links, frontmatter, inline fields, paths and
   ambiguous filenames at the chosen revisions? Which Obsidian services
   must be mirrored to match them?
4. What package/submodule arrangement can reproduce builds and preserve
   upstream licenses? What Node/OS and Obsidian version combinations are
   actually supportable?
5. What can be verified against a real Obsidian oracle, and which behaviors
   or configuration cases must be declared unsupported?

## Runtime spike — 2026-11-19

Environment: Node.js `v26.13.0`, npm `11.20.0`. No `obsidian` executable was
available, so this did not produce same-revision Obsidian oracle results.

### Dataview

- Checked out the exact revision above, ran `npm ci` and `npm run lib`; the
  library build completed. The locked CodeMirror Git dependency needs its
  install scripts to generate `dist` files; `npm ci --ignore-scripts` made
  the build fail with missing `@codemirror/language` declarations.
- The built library imports `obsidian` as an external module, and a direct
  Node import failed with `MODULE_NOT_FOUND`. With only that module stubbed in
  an ephemeral smoke-test runner, the unchanged exported field parser and
  query grammar parsed a field expression and `LIST FROM "Tasks"` in Node.
- This proves a parser subset can be built and exercised with a minimal
  runtime shim; it does not prove index or query execution. `src/index.ts`
  exports `DataviewApi` as a type, not a runtime constructor. The plugin API
  depends on Obsidian's `App`, `MetadataCache`, and `FullIndex`; the index
  itself uses vault events, metadata resolution, a web-worker importer, and
  `LocalStorageCache`. A bridge or a narrower support claim is still needed.
- `DataviewIOApi`'s CSV loader supports HTTP(S) and `file://` paths upstream.
  Any adapter must disable those paths to retain this project's local-only,
  privacy-preserving boundary.
- `npm view obsidian-dataview@0.5.70` returned registry `E404`; the checked
  source revision is not available as that npm package version.

### Breadcrumbs

- `npm view breadcrumbs@4.22.3` returned registry `E404`. The source package
  is plugin-oriented; its `main` entry is `main.js`, and its build requires
  Bun. The WASM build targets `web`.
- Importing the checked-in generated WASM JavaScript directly in Node failed
  because it imports the unresolved source alias `src/logger/index.ts`.
  With an ephemeral Node resolver shim for that logger only, the checked-in
  WASM binary initialized and built a two-node, one-edge graph in Node.
  Outgoing and incoming lookups confirmed the edge remained directed.
  This is evidence for reusing the graph engine, not for running the plugin's
  graph-building pipeline unchanged.
- The graph builder still requires Obsidian's app and metadata cache, plugin
  settings, and (for `dataview_note`) the Dataview plugin API. It runs ten
  explicit edge sources in `EXPLICIT_EDGE_SOURCES`; the nearby rebuild
  JSDoc says nine, so that comment is not a reliable compatibility inventory.

### API typings and Dataview test references

- The official `obsidian` npm metadata (version `1.14.4`) points its `types`
  field at `obsidian.d.ts` and has an empty `main`; it describes the host API
  but does not provide an Obsidian runtime. The `obsidian-typings` package
  (version `6.0.0`) describes extended API types and likewise is not a host
  runtime. These packages were consulted as API-shape references only and
  were not added as runtime dependencies.
- At the pinned Dataview revision, the focused parser and Markdown suites
  `src/test/parse/parse.query.test.ts`,
  `src/test/parse/parse.expression.test.ts`, and
  `src/test/markdown/parse.file.test.ts` passed: 3 suites, 118 tests. They
  cover query keyword case, folder/link/tag sources, expression syntax, and
  frontmatter tag parsing. The initial project tests use the folder-query
  syntax as a reference and copy the upstream `test-vault/tasks/checklist.md`
  fixture, with its MIT notice, to `test/fixtures/dataview/`. The project
  indexes its path only; the broader Dataview cases are not supported by this
  project-defined executor.

### Outcome and remaining gate

The parser and WASM graph engine have narrow Node smoke-test evidence, but
neither full adapter has been exercised unchanged. No joint Dataview /
Breadcrumbs fixture or oracle comparison was possible without Obsidian and
the pinned plugins. The user chose the narrower non-parity scope documented
in the requirements and design; that scope does not rely on either plugin's
broader semantics. Any later parity claim still requires oracle results.
